Why this release matters

Less middleware. More Platform answers.

Moderately technical takeaway: v4 makes the SDK a better product API, not just a storage API. Apps can ask Platform for the shape they need instead of fetching raw documents, rebuilding state locally, and trusting an app-owned database to be the source of truth.

Aggregates are queryable

DashRate can ask "how many?" and "how many per rating?" directly. That is the difference between browsing a pile of reviews and showing a live ratings product.

History is inspectable

A review can be edited, but its prior revisions remain available. Users see the current state while auditors can still inspect change.

Scarcity is enforced

DashMint cards are created only when a fixed-supply token is spent. The cap lives in the contract instead of in app code.

DashRate / Product view

Ratings need more than documents.

A useful ratings app has to answer product questions quickly: total reviews, average score, per-star distribution, filtered reviews, and what changed when someone edited a review.

  • One review per identity per resource via a unique owner/resource index.
  • Rating summaries from count and grouped count queries.
  • Editable reviews with history through retained document revisions.

Why it is exciting: Platform can back user-facing analytics without a separate indexing service becoming the authority.

The average, count, distribution bars, recent reviews, and history are all derived from Platform reads. 

// DashRate review schema
indices: [
  {
    name: "resourceRatingAggregate",
    properties: [{ resourceId: "asc" }],
    countable: "countable"
  },
  {
    name: "resourceRatingDistribution",
    properties: [{ resourceId: "asc" }, { rating: "asc" }],
    countable: "countable",
    rangeCountable: true
  }
]
1 Countdocuments.count gives total reviews for one resource.
2 GroupgroupBy: ["rating"] returns the per-star histogram.
3 Inspectdocuments.history shows previous versions of an edited review.

DashRate / v4 mechanics

Indexes become product primitives.

The new v4 aggregation index flags, countable and rangeCountable, are the key schema unlock. Once the contract declares those paths, the SDK can ask for counts and grouped counts over the same data users are already writing.

documents.count count + groupBy where rating between 1 and 5 documents.history documentsKeepHistory

DashMint Lab / Product view

Digital objects can have rules.

DashMint Lab treats cards as owned Platform documents. They can be minted, transferred, priced, purchased, and burned. More importantly, minting is tied to a fixed supply of DashMint tokens.

  • Ownership is document ownership, not an app database row.
  • Marketplace actions use Platform document operations.
  • Mint capacity is paid for by burning one token per card.

Why it is exciting: scarcity, ownership, and transferability are enforceable by the contract instead of remembered by the UI.

A card is a document with an owner; a listing is a priced document; a purchase changes ownership through Platform. 

// DashMint card document type
card: {
  transferable: 1,
  tradeMode: 1,
  creationRestrictionMode: 0,
  tokenCost: {
    create: {
      tokenPosition: 0,
      amount: 1,
      effect: 1 // burn on create
    }
  }
}
1 Contract defines supply A fixed 100-token DashMint supply is created with the contract.
2 Create spends tokendocuments.create includes tokenPaymentInfo.
3 Card becomes asset The resulting document can be transferred, priced, or purchased.

DashMint Lab / v4 SDK reach

Burn-to-mint is now an app-level pattern.

The v4-specific SDK story is token-paid document creation: documents.create can carry tokenPaymentInfo that satisfies the contract's tokenCost.create. The app does not merely check whether minting is allowed; Platform enforces the payment as part of the write.

tokenCost.create tokenPaymentInfo tokens.identityBalances documents.setPrice documents.purchase documents.transfer
